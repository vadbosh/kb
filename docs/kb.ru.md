# kb — мануал

Хранилище знаний в Markdown на одну линию работы: указатель `00-overview.md` и
пронумерованные файлы `NN-slug.md`. Весь замысел держится на двух свойствах:

- **таблица указателя генерируется** из front matter файлов, поэтому не может
  разойтись с тем, что описывает
- **каждая заметка типизирована по способу устаревания** — `state` и `plan`
  вытесняются более новыми, `reference` и `recipe` правятся на месте, а
  `decision` не устаревает вообще, потому что фиксирует, почему так решили

Зачем это нужно и чего инструмент делать не станет — в
[README.RU.md](../README.RU.md). Этот файл — рабочий мануал: как этим управлять
каждый день и что именно гарантирует каждый механизм.

| Слой | За что отвечает | Где живёт |
|---|---|---|
| Skill `kb` | суждение — что писать, куда, что читать | каталог скиллов ассистента |
| CLI `kb` | механика — номера, таблица, детект дрейфа | `<skill-dir>/scripts/kb` |

Скилл подгружает одну половину по надобности: `references/save.md` на запись,
`references/restore.md` на чтение. Обращение — словами `kbsave` и `kbrestore`,
слэш-форма `/kb save` и `/kb restore`.

Обычная работа shell не трогает — скилл сам зовёт CLI. Единственное штатное
исключение: `kb adopt`, однократно на каждый переносимый каталог.

Установка, настройки и удаление — в [README.RU.md](../README.RU.md#установка).

## Рабочий цикл — что набирать и когда

### Сессия 1, новый проект

Готовить заранее нечего — но и само ничего не появится. **Запуск ассистента
`kb/` не создаёт.** Каталог возникнет в тот момент, когда ты первый раз скажешь
`kbsave`, и до тех пор его в проекте просто нет.

```
$ cd /path/to/project
$ claude
```

Работаешь как обычно, kb не участвует:

```
> разберись почему fluent-bit не доезжает до базы
```

Хочу сохранить:

```
> kbsave
```

Скилл сам: `kb status` (пусто → создаст `kb/`), выберет `kind`, сформулирует
`title`, напишет файл, пересоберёт индекс. Ответит счётчиками:

```
kb: создан /path/to/project/kb, +1 reference (01-fluentbit-pipeline.md). Индекс собран.
```

Бэйр `kbsave` = «сам реши что из сессии durable». Задать тему явно —
`kbsave про конвейер fluent-bit`.

Ещё промпт, ещё решение, снова сохранить:

```
> почему terraform init падает с text file busy
...
> kbsave
```

Это грабля → `kind: recipe`. Такого файла ещё нет → заведёт новый:

```
kb: +1 recipe (02-traps-and-recipes.md). Индекс собран.
```

Третья грабля **дописалась бы в тот же** `02-traps-and-recipes.md`, а не плодила
файлы. Это и есть решение «дописать или новый».

Вышел: `/exit`.

### Сессия 2, возврат

```
$ claude --resume <ID>
```

Нужен предыдущий срез:

```
> kbrestore
```

Скилл делает `kb status` + `kb check`, читает указатель и актуальный `state`, и
сверяет с тем, что уже в переписке. Один из трёх ответов:

| Что нашёл | Что скажет |
|---|---|
| срез тот же, `check` чист | «контекст актуален, перечитывать нечего» — токены не тратит |
| появился более новый `state` | читает его: «ситуация изменилась, вот что» |
| `check` дал дрейф (выход 3) | «заметки правили без sync» — читает изменённые файлы, а не таблицу |

Дальше брифинг: состояние / что открыто / какие файлы читать под задачу.

Возобновился сразу и на диске никто ничего не менял → `kbrestore` можно не звать,
всё в переписке. Он нужен когда **прошло время** или **работала другая сессия**.

Получил решение, сохранить:

```
> kbsave
```

Файлы уже есть, поэтому чаще будет **дописывать**. На этом этапе обычно уместен
срез:

```
> kbsave срез состояния
```

→ `03-state-2026-08-07.md`, указатель сам пометит его актуальным, а прежний —
`⏳ (прежний срез)`.

### Шпаргалка

| Момент | Ввод |
|---|---|
| записать что выяснили | `kbsave` |
| записать конкретно про X | `kbsave про X` |
| зафиксировать состояние на дату | `kbsave срез состояния` |
| вернулся в сессию, нужен контекст | `kbrestore` |
| что вообще есть в заметках | `kbrestore` |

`kbsave` и `kbrestore` — обычные слова в промпте, скилл их подхватывает.
`/kb save` и `/kb restore` — явная слэш-форма, делает ровно то же.

Shell руками не нужен — скилл зовёт `kb` сам. Исключение одно: `kb adopt`,
разово, для миграции старого каталога.

## Как записывать

```
kbsave
kbsave про грабли с terraform init
```

Скилл делает всё сам:

1. `kb status` — что уже есть
2. решает: **дописать** в существующий файл или **завести новый**
   - дописать — если это ещё один случай того же, что файл уже покрывает
   - новый — если отвечает на другой вопрос, либо это `state`/`decision`
     (точки во времени, их не дописывают)
   - делить существующий — если >~400 строк **и** секции про разное
3. выбирает `kind`, пишет `title` от лица читателя («что мне нужно», не «как
   документ называется»)
4. `kb add` → пишет тело → `kb sync` → `kb check`
5. отчитывается счётчиками: `+1 decision (04-why-x-target.md), edited 03-traps.md`

Нечего записывать → скажет `Nothing durable for kb.`, пустых файлов не создаст.

### Пять kind

| kind | что | вытесняется новым |
|---|---|---|
| `state` | срез на дату: что сделано, что открыто | да, более поздней датой |
| `plan` | что запланировано, порядок | да, при выполнении |
| `decision` | решение и **почему** | нет, только `--supersedes` |
| `reference` | как устроено | нет, правится на месте |
| `recipe` | грабли и команды проверки | нет, правится на месте |

`state` получает сегодняшнюю дату в имя автоматически.

## Возврат в старую сессию

```
kbrestore
```

`claude -r` восстанавливает переписку, но файлы могли уехать: правил ты, правила
другая сессия, или компакт сжевал детали. Агент помнит одно — на диске другое.

`kbrestore` делает именно эту сверку:

1. `kb status` — какой срез актуален **сейчас**
2. `kb check` — индекс не разошёлся с файлами
3. читает указатель, читает актуальный срез
4. **сравнивает с тем, что в переписке**, и говорит прямо:
   - срез тот же, `check` чист → контекст актуален, перечитывать нечего
   - появился более новый `state` → читает его, ситуация изменилась
   - `check` дал дрейф → заметки правили без sync, читает изменённые файлы

Потом брифинг: состояние / что открыто / какие файлы читать под задачу /
расхождения. Не дамп файлов — синтез. Остальные файлы открываются по мере
надобности, по колонке «что нужно» в указателе.

Автоматом при старте сессии это не срабатывает — вызывается явно. Хук
`SessionStart` для этого не нужен: сверка нужна тогда, когда ты садишься за
работу, а не при каждом запуске ассистента.

## Как обновляется индекс

Источник правды — **front matter файлов**, таблица это проекция.

```
kb/01-pipeline.md              kb/00-overview.md
---                            <!-- kb:begin -->
title: как устроен конвейер ─┐  | что нужно | файл | тип | обновлён |
kind: reference              ├─►| как устроен конвейер | `01-pipeline.md` | reference | ... |
updated: 2026-09-01         ─┘  <!-- kb:end -->
---
```

`kb sync` читает front matter всех `NN-*.md` и переписывает **только** текст
между маркерами. Остальное в указателе — байт в байт как было.

| Действие | Индекс |
|---|---|
| `kb add` (внутри `kbsave`) | пересобирается сразу |
| правка `title`/`kind`/`updated` | нужен `kb sync` |
| файл удалён/переименован | нужен `kb sync` |

Между правкой и sync индекс устаревший — `kb check` ловит (`index table is
stale`, выход 3). `kbsave` вызывает sync и check сам.

**Считается автоматически, руками не пишется:**

- актуальный срез — max дата среди `state`, отдельной строкой над таблицей
- прежние срезы помечаются `⏳ (прежний срез)`
- порядок строк — по номеру файла: правка одного файла не перетасовывает таблицу
- номер нового файла — следующий свободный; дыры не переиспользуются (номер, на
  который когда-то ссылались, не должен указать на другой файл)

## CLI — справочник

| Команда | Что |
|---|---|
| `kb status` | где kb, сколько файлов, какой срез актуален, самые крупные |
| `kb check` | расхождения механики; выход 3 если есть |
| `kb verify` | подозрения: пропавшие пути, залежавшиеся заметки; выход 3 |
| `kb sync` | пересобрать таблицу из front matter |
| `kb add <slug> --kind <k> --title "..."` | новый файл + front matter + пересборка |
| `kb list [--scan DIR] [--prune]` | все известные kb: где лежат, что внутри |
| `kb outline [файл]` | карта разделов с весами — где швы для дробления |
| `kb init [--title ...]` | только скелет указателя |
| `kb adopt [--apply] [--in-place]` | миграция существующего каталога |
| `--dir X` | работать в X вместо `./kb` |

`kb check` ловит: устаревшую таблицу, ссылки на удалённые файлы, файлы без front
matter, `.md` вне схемы `NN-slug.md`, оставшиеся `.bak`, **файлы за порогом
размера**.

### Размер файлов

Правило «не больше 200 строк» — про файлы инструкций (`CLAUDE.md`, `rules/*.md`,
`SKILL.md`), которые грузятся в контекст **всегда**. Файлы kb читаются по
выбору, поштучно, поэтому порог другой и мягче:

| Порог | Что значит |
|---|---|
| 400 строк | посмотреть, не про разное ли секции |
| 1200 строк | один `Read` обходится дорого; файл помечается в индексе `⚠ ~Nk токенов` |

**Размер сам по себе не повод дробить.** Длинный связный `reference` — хороший
файл. Настоящий критерий — смешение `kind` в одном файле, потому что `kind` это
и есть «на какой вопрос отвечает». Судить по `kb outline`: карта из десятка
заголовков вместо чтения полутора тысяч строк.

Автодробления нет и не будет: где резать — решение про смысл. Но и мониторить
руками не надо — `kbsave` вызывает `kb check` в конце каждой записи, и скилл
обязан отреагировать на предупреждение о размере в том же ходе.

### Проверка на правду

`check` сверяет индекс с файлами — **внутреннюю согласованность**, а не
соответствие реальности. За это отвечает отдельная команда:

```bash
kb verify
```

Она даёт **подозрения**, а не дефекты, поэтому вынесена из `check`: тот
однозначен и механичен (выход 3 = устранить), эта работает эвристикой (выход 3 =
проверить глазами). Объединять их нельзя: точный сигнал растворится в
предположениях.

**Пути.** Проверяются только те, что в бэктиках И у которых существует корень
(первые два компонента). Замер на живом kb: без этих двух условий выходит 271
флаг на 296 путей, из них настоящих ~2 — URL-и (`/stats/prometheus`), версии API
(`/v1alpha1`), обрубки длинных путей. С условиями — 6 флагов, 2 настоящих.
Обратная сторона: путь в код-блоке без бэктиков не проверяется. Осознанный
компромисс — при обратном соотношении отчёт быстро перестают читать.

**Возраст по kind.** Не «неправда», а «сюда давно не смотрели»:

| kind | порог |
|---|---|
| `recipe` | 120 дней — устаревает вслед за инструментами |
| `reference` | 180 дней |
| `decision` | **не проверяется** — «почему так решили» остаётся правдой всегда |
| `state`, `plan` | не проверяются — вытеснение уже работает |

**Чего `verify` не умеет**: подтвердить утверждение о живой системе («NLB
называется так-то», «CRD в AU нет»). Для этого нужен запрос к самой системе —
это дорого, требует доступов, и регулярно гонять `terraform`/`kubectl` на проде
никто не станет. Рассуждения («почему X-Target, а не Host») не проверяемы в
принципе.

### Реестр

`kb list` показывает все известные каталоги заметок. Реестр —
`~/.local/state/kb/registry.txt` (переопределяется `KB_REGISTRY`), пополняется
сам при создании kb, проверяется на живость при чтении:

```bash
kb list                    # все kb: путь, файлов, актуальный срез, крупные
kb list --scan /projects       # подобрать заведённые до реестра или руками
kb list --prune            # убрать записи, у которых пропал указатель
```

Заметки всегда в `kb/`. Рядом с «висячим» `00-overview.md` команды `add`/`init`
откажутся работать — иначе два набора заметок в одном каталоге. Обход:
`adopt --in-place`, только если снаружи ссылаются на старые пути.

## Чего не делать

- Не править таблицу внутри `kb:begin`/`kb:end` — затрётся первым же sync.
- Не переписывать прозу вне маркеров — она человеческая.
- Не класть креды. Ссылаться на механизм (секрет в кластере, переменная), не на
  значение.
- Не дублировать доку, живущую рядом с кодом — она правится вместе с кодом.
  Указать её путь.
- Не вести дневник. `state` — срез, а не хроника «что делали во вторник».

## Язык

Диагностика инструмента (`check`/`list`/`outline`/`status`) — английская.
Текст, который пишется **внутрь** заметок (шапка таблицы, строка «Актуальный
срез», скелет указателя), идёт по `KB_LANG`: по умолчанию `ru`, для английского
`KB_LANG=en kb ...`. Новый язык — один ключ в словаре `STRINGS` внутри CLI,
больше ничего менять не надо.

Триггер-фразы скиллов двуязычные («запиши в kb» и «save to kb» работают оба),
тела скиллов английские — их читает LLM.
