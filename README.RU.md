# kb

**Хранилище знаний в обычном Markdown. Индекс обновляет агент — сам, по ходу
сессии. У каждой заметки указано, как она устаревает.**

Годится для чего угодно, что иначе копится грудой `.md` — миграция, инцидент,
исследование, ремонт квартиры, судебное дело. К коду отношения не имеет.

## Идея

Почти у каждого со временем заводится своя вики. Устроена она обычно так: есть
список файлов, а рядом лежат сами файлы, на которые этот список ссылается. Пока
файлов немного, список и файлы сходятся.

Потом файлы добавляют, переименовывают, делят на части. После каждого такого
раза список надо править руками. Однажды список править перестают. С этого
момента список и файлы расходятся, и выглядит это так:

- в разделе «текущее состояние» стоит дата, которую никто не обновил;
- ссылки ведут на файлы, которые давно переехали;
- рядом с каталогом растёт стопка `00-overview.md.bak.*` — по копии на каждую
  попытку привести список в порядок.

Мы сделали скилл, который эту задачу решает. В нём три механизма. Первые два не
дают списку отстать от файлов. Третий ничего не чинит: он показывает, где список
уже отстал от файлов.

### 1. Индекс генерируется, а не поддерживается

Каждая заметка начинается с трёх полей front matter — вот начало файла
`kb/02-pipeline.md`:

```yaml
---
title: как устроен конвейер
kind: reference
updated: 2026-08-05
---
# дальше обычный текст заметки
```

Указатель — это `kb/00-overview.md`. Его создаёт первый же `/kb save`: заголовки,
раздел с правилами и абзац о том, что за работа. Дальше этот текст живёт как
обычный текст — его дописывает ассистент по ходу дела или ты правишь руками.

Внутри указателя есть участок между двумя маркерами. Только его kb и собирает
заново — из front matter всех заметок:

```markdown
## С чего начинать чтение          ← твой текст, kb его не трогает

<!-- kb:begin -->                 ← отсюда и до kb:end всё генерируется
Актуальный срез: `21-state-2026-08-07.md` (2026-08-07).

| что нужно                             | файл             | тип       | обновлён   |
|---------------------------------------|------------------|-----------|------------|
| как устроен конвейер                  | `02-pipeline.md` | reference | 2026-08-05 |
| известные проблемы и команды проверки | `23-traps.md`    | recipe    | 2026-08-07 |
<!-- kb:end -->

Снова обычный текст: что за работа, чего сюда НЕ пишем, куда смотреть ещё.
```

Строку про актуальный срез и таблицу не правит никто — ни ты, ни ассистент: они
пересобираются из файлов при каждом `kb sync`, и правка внутри маркеров пропадёт.
Разойтись с файлами такая таблица не может — она из них и получена. Всё, что вне
маркеров, kb не трогает никогда.

### 2. Знание типизировано по способу устаревания

В обычной вики все страницы равноправны: по самой странице не видно, описывает
она текущее положение дел или прошлое. А устаревают они по-разному — вот два
файла из одного каталога:

- `02-pipeline.md`, «как устроен конвейер сборки логов». Верно месяцами. Что-то
  поменялось в конвейере — файл правится на месте, прежний текст никому не нужен.
- `15-state-2026-08-05.md`, «что сделано и что осталось на 5 августа». Верно
  ровно на 5 августа. Через неделю это **не ошибка**, а исторический факт:
  переписывать его нельзя, рядом появляется новый срез, а этот остаётся как
  свидетельство того числа.

Первый файл живёт и правится, второй фиксируется и вытесняется. Если оба лежат в
одном списке без признака типа, читатель не может отличить одно от другого — и
начинает сомневаться в обоих. kb требует указать тип явно, полем `kind`.

| kind | что хранит | как стареет |
|---|---|---|
| `charter` | зачем это существует, границы, чего *сознательно не* делаем | правится на месте — один на kb |
| `state` | срез на дату | **вытесняется** более поздним |
| `plan` | что запланировано, в каком порядке | вытесняется по выполнении |
| `decision` | решение и **почему**; отвергнутые варианты | **не устаревает** — исторический факт |
| `reference` | как что-то устроено | правится на месте |
| `recipe` | известные проблемы и готовые команды проверки | правится на месте |

Что из этого следует автоматически:

- **Актуальный срез вычисляется**, а не объявляется — это `state` с наибольшей
  датой в имени файла. Прежние помечаются, но не удаляются: каждый остаётся
  достоверным описанием состояния на свою дату.
- **`decision` никогда не переписывается.** Отмена решения — это новое решение,
  которое вытесняет прежнее. Рассуждение, приведшее к старому выбору, остаётся
  читаемым, а через полгода обычно именно оно и нужно.

### 3. Устаревание отслеживают две независимые проверки

```
kb check     механика: индекс против файлов, битые ссылки, front matter, размер
kb verify    подозрения: пропавшие пути, заметки, куда давно не заглядывали
```

Намеренно **разделены**. `check` даёт однозначный вердикт: выход 3 означает
дефект, который надо устранить. `verify` работает эвристикой: выход 3 означает
повод посмотреть глазами. Объединить их — значит смешать точный сигнал с
предположением и обесценить первый.

Ни одна из проверок не берётся судить, соответствует ли утверждение внешней
реальности. В `recipe` может лежать команда, которая это подтвердит, но запускать
её на проде по расписанию — не задача инструмента для заметок.

## Установка

Нужен **Python 3.10+** и больше ничего. Ни pip, ни пакетов, ни sudo.

```bash
git clone https://github.com/vadbosh/kb && cd kb

./install.sh              # Linux / macOS
./install.sh --dry-run    # напечатать что будет, ничего не менять
./install.sh --with-path  # плюс положить kb в PATH, для запуска руками
```

```powershell
.\install.ps1             # Windows
.\install.ps1 -DryRun
.\install.ps1 -WithPath

# если execution policy блокирует файл:
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

Оба проверяют Python прежде, чем что-то тронуть. Нет Python или он не в PATH —
установщик останавливается и пишет цветом, что делать. На Windows так бывает
часто: при установке Python не отметили «Add python.exe to PATH».

Всё складывается в один каталог на ассистента:

```
<skills-dir>/kb/SKILL.md
<skills-dir>/kb/references/*.md
<skills-dir>/kb/scripts/kb        + лончер kb.cmd на Windows
```

Ничто не зависит от `PATH` или от существования `~/.local/bin` — на Windows такого
каталога просто нет, и по той же причине Windows-установщик пишет `.cmd`-лончер
(shebang там не работает).

Пишется только в те каталоги ассистентов, которые уже существуют; перебить
автоопределение можно флагом `--skills-dir <путь>` / `-SkillsDir <путь>`.
Установка руками сводится к `cp -r skills/kb <skills-dir>/` — скилл
самодостаточен.

Установщик можно запускать повторно: файлы, которые не изменились, он не
перезаписывает вовсе. Заменяемый файл он копирует рядом под именем
`<файл>.bak.<дата-время>` — но **только если такого содержимого нет в
репозитории**. Правка руками единственное, чего не вернёт `git checkout`; копия
всего остального сохраняла бы то, что и так восстановимо.

## Использование

Что нужно сделать, по порядку:

1. **Установить** — `./install.sh` (Linux/macOS) или `.\install.ps1` (Windows).
   Раздел [Установка](#установка).
2. **Зайти в каталог проекта** и запустить там ассистента.
3. **Написать `/kb save`.** Именно этот шаг создаёт каталог заметок и пишет
   первую заметку. До него в проекте нет никакого — запуск ассистента его не
   создаёт, и это нормально.

Каталог называется `kb/`, если только он уже не занят самим проектом: имя
обычное, и там могут лежать исходники, точка монтирования или чья-то заготовка.
Тогда kb не пишет в каталог, который создал не он, — пустой или нет, — и
возвращает выбор:

- **`./.kb`** — второе имя, по которому kb тоже ищет, поэтому дальше ничего
  указывать не нужно;
- **этот каталог всё-таки под заметки** — перезапустить с `KB_ALLOW_EXISTING=1`;
- **другое место** — `--dir <путь>`, но указывать его придётся каждой следующей
  команде.

Со второй сессии разницы нет: заметки находятся из любого места внутри проекта,
под любым из двух имён.

Дальше вся работа — две команды:

```
/kb restore    первым делом, когда садишься за работу — загрузит заметки,
               скажет что изменилось
/kb save       когда появилось что сохранить
```

Всё. `kb` в терминале ты не запускаешь — это делает ассистент.

Имя любой команды работает и само по себе — `/kb check`, `/kb status`, `/kb list`.
Ассистент выполнит её и покажет вывод: ничего не загрузит и не запишет.

Отдельных команд `/kbsave` и `/kbrestore` не существует: скилл называется `kb`,
поэтому команда одна — `/kb`, а половина выбирается первым словом. Слова «kbsave»
и «kbrestore» в обычной фразе обычно тоже срабатывают — они перечислены в
описании скилла, — но это распознавание, а не команда.

<details>
<summary>Что за этими двумя стоит</summary>

| Команда | Под капотом |
|---|---|
| `/kb restore` | `kb status` + `kb check` + `kb verify`, затем указатель и актуальный срез, затем только нужные задаче файлы |
| `/kb save` | `kb status` → решает дописать-или-новый → `kb add` → пишет тело → `kb sync` → `kb check` |

</details>

### Если заметки уже есть

Каталог с рукописным указателем и пронумерованными файлами переносится так:

```bash
kb adopt              # превью: что переедет, какие заголовки подберёт
kb adopt --apply
```

Заметки переезжают в `kb/`, добавляется front matter, вставляются маркеры,
собирается таблица. Заголовки **берутся из твоей существующей таблицы**, а не
выдумываются из `# H1`. Формулировка, написанная человеком для читателя,
отвечает на вопрос «что мне нужно»; название документа на него не отвечает.
Потеряешь её — потеряешь смысл всей затеи. Копия каждого изменённого файла
сохраняется рядом.

### Чтобы заметки нашли и без kb

Заметки прочитает тот, кто запустит `/kb restore`. Человек, который про заметки
не знает, эту команду не запустит никогда. А файл в корне проекта агент читает
всегда — с него и начинает.

```bash
kb route
```

Команда `kb route` пишет в корень проекта два файла. Первый — `AGENTS.md`: в нём
указатель на заметки, charter и актуальный срез. Второй — `CLAUDE.md`, в нём
одна строка `@AGENTS.md`.

Файла два, потому что Claude Code читает `CLAUDE.md` и не читает `AGENTS.md`, а
Codex и Opencode читают `AGENTS.md`. Сам текст при этом лежит только в
`AGENTS.md`, а `CLAUDE.md` его импортирует.

Команду `kb route` вызывает и `/kb save` — когда создаёт каталог `kb/` в проекте,
где `AGENTS.md` ещё нет. Если `AGENTS.md` в проекте уже есть, `/kb save` только
предложит запустить `kb route`, а сам файл не тронет.

Внутри маркеров `kb:begin` и `kb:end` лежит то, что kb выводит из заметок. Этот
блок обновляют команды `kb route` и `kb sync`. Снаружи маркеров лежит твой текст:
команды проверки и определение готовности. `AGENTS.md` без маркеров kb не трогает
и писать в него отказывается. В `CLAUDE.md` без импорта kb тоже ничего не пишет,
а печатает строку, которую надо добавить руками.

Оба файла попадают в контекст на старте каждой сессии, поэтому их суммарная длина
ограничена 200 строками — вместе с импортами и `CLAUDE.local.md`, их хост тоже
разворачивает на старте. Предел считается на каталог запуска: сессия в
подкаталоге грузит его `CLAUDE.md` поверх всех вышестоящих, и `kb route` с
`kb verify` сообщают про такие цепочки тоже. Сокращать эти файлы kb не станет: за
маркерами лежит твой текст.

### В репозитории или только на этой машине

Заметки внутри git-репозитория коммитятся по умолчанию: их забирает `git add -A`.
kb говорит об этом один раз — когда создаёт каталог `kb/`.

```bash
kb local          # .git/info/exclude — заметки остаются здесь, и
                  # точка входа, написанная kb, уходит туда же
                  # либо закоммитить, и они поедут вместе с проектом
```

`.git/info/exclude` действует на один рабочий каталог, а `.gitignore` — на всех,
кто клонирует репозиторий. Свой выбор kb нигде не записывает: `kb status` каждый
раз спрашивает git.

## Чего kb намеренно не делает

- **Не дробит длинные файлы сам.** О размере он сообщает, но ничего не
  запрещает. Длинный связный `reference` — нормальный файл; где именно резать —
  вопрос смысла, а не числа строк. Чтобы принять решение, `kb outline` печатает
  карту разделов: хватит десятка строк вместо полутора тысяч.
- **Ни базы данных, ни сервера, ни привязки к инструменту.** Заметки — обычный
  Markdown в твоём репозитории. Удалишь инструмент — они останутся читаемыми,
  перестанет обновляться только таблица.
- **В твой текст не вмешивается.** Генерируется единственное место — управляемый
  блок.

## Два слоя

| Слой | За что отвечает | Где живёт |
|---|---|---|
| CLI `kb` | всё **механическое** — нумерация, таблица, выявление расхождений, какой срез актуален | `<skill-dir>/scripts/kb` |
| Skill `kb` | всё, где нужно **суждение** — новый файл или существующий, какой `kind`, не начал ли файл отвечать на два разных вопроса | каталог скиллов ассистента |

Это разделение и есть замысел. Ни одна сторона не берётся за работу другой: CLI
не пытается понять смысл заметки, ассистент не правит таблицу руками.

У скилла две половины, каждая подгружается только когда нужна:

```
kb/SKILL.md               роутинг + правила, общие для обеих половин
kb/references/save.md     запись: дописать или новый файл, какой kind, заголовки
kb/references/restore.md  чтение: сориентироваться, читать выборочно, брифинг
kb/references/entry-point.md  только когда команда напечатала ⚠ про AGENTS.md
kb/scripts/kb             CLI — одна копия, без зависимости от PATH
```

Написано под ассистентов, читающих `SKILL.md` — Claude Code, Opencode, Codex.
CLI работает и сам по себе, если удобнее гонять руками.

## Команды

| Команда | Что делает |
|---|---|
| `kb status` | где kb, сколько файлов, какой срез актуален, самые крупные |
| `kb brief` | указатель и актуальный срез дословно — один и тот же вывод при одних и тех же файлах |
| `kb check` | механические расхождения; выход 3 = чини |
| `kb verify` | подозрения: пропавшие пути, залежавшиеся заметки, работа, ушедшая вперёд записей |
| `kb sync` | пересобрать таблицу из front matter |
| `kb add <slug> --kind <k> --title "…"` | следующая нумерованная заметка + front matter + пересборка |
| `kb outline [файл]` | карта разделов с весами — где швы для дробления |
| `kb list [--scan DIR] [--prune]` | все kb, известные на этой машине |
| `kb streams [--sessions N]` | где стоит сессия, затем какие каталоги трогала — читается из стенограммы |
| `kb adopt [--apply] [--in-place]` | миграция рукописного каталога заметок |
| `kb hook --install` | git pre-commit, отклоняет коммит при коде 4 |
| `kb route` | `AGENTS.md` в корне проекта, чтобы заметки нашли и без kb; `CLAUDE.md` его импортирует |
| `kb local [--dry-run]` | оставить заметки на этой машине (`.git/info/exclude`) |
| `--dir X` | работать в X вместо `./kb` или `./.kb` |

## Настройки

| Переменная | По умолчанию | Что определяет |
|---|---|---|
| `KB_LANG` | `ru` | язык текста, который пишется **внутрь** заметок — шапка таблицы, строка «Актуальный срез», скелет указателя. Диагностика всегда английская. |
| `KB_REGISTRY` | `$HOME/.local/state/kb/registry.txt` | где лежит список известных каталогов kb |
| `KB_DOC_DIR` | `$HOME/.kb-docs` | куда ставить мануал |
| `KB_BIN_DIR` | `$HOME/.local/bin` · `%LOCALAPPDATA%\kb\bin` | куда ставить необязательную копию в PATH |

**kb запоминает язык, на котором его завели** — он записан в маркере
`kb:begin` внутри обзора. Каждая следующая команда читает его оттуда, поэтому на
одной машине уживаются два потока на разных языках, а kb, склонированный на
машину с другими настройками, остаётся на своём. `KB_LANG` решает только для
того kb, у которого языка ещё нет.

Направить `KB_LANG` на существующий kb — не переключение, и `kb check` об этом
скажет. Переключение настройкой не делается. На следующем `sync` сменятся маркер
и шапка таблицы, а заголовки заметок, проза вне маркеров и заполненные разделы
точки входа написаны руками и останутся прежними. Файл окажется наполовину на
каждом языке. Чтобы переключить по-настоящему: перевести эти три вещи руками, а
потом `KB_LANG=<новый> kb sync`. Новый язык — один ключ в словаре `STRINGS` внутри CLI.

Ни один путь нигде не прибит к конкретной машине.

## Секреты

`kb check` ищет в заметках учётные данные при каждом запуске — то есть при
каждом `/kb save`, потому что скилл вызывает его там. Слоя два, и отчёт всегда
говорит, какой из них отработал:

```
secrets: none found — checked with built-in patterns + trufflehog 3.95.3
secrets: none found — checked with built-in patterns only
         install gitleaks or trufflehog for the full ruleset
```

**Слой 1, всегда** — пятнадцать шаблонов, ничего ставить не надо, работает
везде. Двенадцать ловят форму с опознаваемым префиксом или заголовком: ключи AWS,
токены GitHub, Slack, Google, Stripe, OpenAI и Atlassian, приватные ключи PEM,
JWT, пароль внутри строки подключения, `IDENTIFIED BY '…'` в SQL.

Ещё три требуют **имя переменной и форму значения одновременно** — потому что у
самого секрета префикса нет: секретный ключ AWS это сорок символов base64 и
больше ничего. У `aws_secret_access_key = <40 base64>` невинного прочтения не
существует, а у голого сорокасимвольного токена их сколько угодно. Каждый из этих
трёх перед добавлением был замерен на обоих живых каталогах: ноль срабатываний,
то есть с обычным текстом они не пересекаются.

**Слой 2, если найдётся** — `gitleaks`, `trufflehog` или `detect-secrets`,
первый обнаруженный в PATH, поверх того же каталога. Примерно 150 правил вместо
десяти. Отсутствие утилиты не ошибка: покрытие уже, и об этом сказано в отчёте.

Находка даёт код возврата **4**, отдельный от 3 для обычных расхождений — чтобы
хук или конвейер отличали «таблица устарела» от «в заметке лежит ключ».

### Чего проверка не ловит

Энтропийный слой был написан и убран. На двух настоящих каталогах заметок он дал
четыре находки, все четыре ложные: путь к файлу, значение конфига, имя пода
Kubernetes и снова путь. Идентификаторы и пути длинные и выглядят случайно,
порога, отделяющего их от токена, не нашлось. Отчёт с таким соотношением
перестают читать за пару дней.

Поэтому **короткий пароль посреди фразы не ловится ничем** — ни встроенными
шаблонами, ни gitleaks, ни trufflehog. Автор gitleaks признаёт это ограничение
прямо. Проверка снижает риск, но не заменяет правило не писать секреты в заметки.

### Как проверять сам детектор

Ключ с корректным форматом неотличим от рабочего — ни для этой проверки, ни для
чужих. **Не коммить образцы учётных данных как тестовые фикстуры**, даже
поддельные: их подхватит и собственное сканирование GitHub, и сканеры всех, кто
склонирует репозиторий. Генерируй их внутри теста из шаблона, чтобы правдоподобное
значение никогда не оказалось в файле.

То же касается самих заметок: поддельный ключ, вставленный «посмотреть, что
будет», для любого инструмента является настоящей находкой.

### Блокировка коммита

```bash
kb hook --install     # git pre-commit, отклоняет коммит при коде 4
```

Имеет смысл, только если заметки лежат внутри git-репозитория. Многие не лежат —
тогда работающий контроль это `kb check` в конце каждой записи, он выполняется
в любом случае.

## Заметки по устройству

Что стоит знать, прежде чем дописывать инструмент:

- **Освободившиеся номера повторно не выдаются.** На номер, который когда-то
  принадлежал файлу, могут до сих пор ссылаться из сообщения коммита или из
  другой заметки.
- **Порядок строк — по номеру**, поэтому правка одного файла не перетасовывает
  таблицу: изменение в истории git остаётся небольшим.
- **`verify` проверяет только пути, взятые в обратные кавычки, и только если
  существует их корень.**
  Замер на живом kb из 19 файлов: без этих двух условий получается 271 флаг, из
  которых настоящих около двух — URL-адреса, версии API, обрубки длинных путей. С
  условиями: 6 флагов, 2 настоящих. При первом соотношении отчёт перестают
  читать через пару дней. Цена — путь внутри блока кода не проверяется. Путь вида
  `~/…` считается абсолютным; проверяются заметки, обзор и точка входа.
- **Пороги размера — 400 и 1200 строк.** Известное правило «не больше 200 строк»
  относится к файлам инструкций: те попадают в контекст на каждом ходу. Файлы kb
  читаются по требованию и по одному, поэтому правило на них не распространяется.
- **Front matter разбирается без библиотеки YAML** — плоские пары `key: value`
  между `---`, деление по первому двоеточию, чтобы двоеточие могло встречаться и
  в самом заголовке.

## Тесты

```bash
python3 tests/test_kb.py          # несколько секунд, только стандартная библиотека
python3 tests/test_kb.py -v       # по строке на тест
python3 tests/test_kb.py Guards   # одна группа
```

Каждый запуск получает временный каталог со своими `HOME` и `KB_REGISTRY`, так
что настоящие заметки и настоящий реестр не затрагиваются.

Тест покрывает одно из двух:

- **запрет, ради которого инструмент и существует** — запись за пределы
  текущего каталога, в `$HOME`, в каталог из `PATH`;
- **ошибку, которая однажды дошла до пользователя** — её версия названа прямо в
  тесте.

Намеренно **не** проверяется, полезна ли заметка: это пробовали, замерили на 19
живых заметках и отказались, потому что ни один механический признак не отделил
достаточные заметки от недостаточных.

## Удаление

```bash
rm -rf <skills-dir>/kb
rm -f  ~/.local/bin/kb        # только если ставили с --with-path
rm -rf ~/.local/state/kb      # реестр
rm -rf ~/.kb-docs
```

Заметки не тронуты — они никогда не были внутри инструмента.
